## 数据模型约定

### 用户隔离（关键）

- 所有业务表**必须**带 `owner_id`（批次 2 起）。
- 查询一律走 API 层注入的当前用户，强制 `WHERE owner_id = :uid`，不靠业务代码自觉。
- 共享功能尚未实现，但表结构预留：未来加 `visibility` 字段与关联表即可，不需要迁移历史数据。

### 时间戳

- 所有 `DateTime` 列一律 `timezone=True`。
- ⚠️ **SQLite 读回来的 datetime 是 naive 的**，PG 是 aware 的。任何比较前必须过
  `app.core.time.as_aware()`，否则在 SQLite 上测试通过、在 PG 上反而没事，或者反过来炸。

### 令牌

| | 存放 | 有效期 | 用途 |
|---|---|---|---|
| access token | 前端内存 | 30 分钟 | 每个请求的 `Authorization: Bearer` |
| refresh token | 前端 localStorage | 30 天 | 换新 access token；**库里只存 sha256 摘要** |

- **轮换**：每次刷新都吊销旧会话、签发新会话。旧令牌重放直接 401。
- **改密**：吊销该用户全部会话，强制所有设备重新登录。
- **设备管理**：`user_sessions` 一行 = 一台设备，可在设置页单独吊销。

## 标签体系（批次 2）

单品与搭配是**两套完全独立的标签体系**：同一张表、同一个 `owner_id`，靠 `scope` 列
（`garment` / `outfit`）隔开，互不可见。

### 结构：两层类别 + 一层级联

标签是 **类别 → 取值** 两层，外加一层「取值挂取值」用来做级联：

- `tag_categories.parent_category_id` —— 声明本类别是谁的子级。`NULL` = 顶层类别。
- `tag_values.parent_value_id` —— 本取值挂在父类别下的哪个取值上。`NULL` = 未归类。

于是「选了大类=外套，小类只列风衣/西装外套」不需要额外的表。**只允许两层**：
父类别本身必须是顶层类别（想再深一层直接 400）。

两个外键都是 **`ON DELETE SET NULL`，不是 `CASCADE`**：删「大类」只把「小类」降级成
顶层类别，删大类取值「外套」只把「风衣」变成未归类 —— 不该顺手抹掉用户的另一份数据。
（`routes/tags.py` 里另外显式做了降级，不依赖 SQLite 的外键强制。）

### 初始化建什么

| scope | 类别（骨架） | 预置取值 |
|---|---|---|
| `garment` | 大类 / 小类 / 颜色 / 材质 | 大类 8 个、**颜色一套 20 个** |
| `outfit` | 季节 / 风格 / 色系 | 季节 4 个 |

级联关系：`小类 → 大类`。其余（颜色 / 材质 / 风格 / 色系）彼此正交，都是顶层类别。

### 为什么这样初始化

**建骨架，不塞内容。** 分类骨架各家差异极大（有人按场合分、有人按品牌分），
一次性塞四五个**带取值**的类别进筛选栏只会添乱；但类别轴本身留着，用户想用就直接
往里填，不用先想「我该不该建一个类别」。

- **大类**：任何衣橱都绕不开的第一层，取值近乎通用，预置是帮忙。
  参考国内电子衣橱类 App（小可衣橱 / 电子衣橱 / 无忧衣橱），划分收敛到
  「上装 / 下装 / 裙装 / 外套 / 鞋 / 包 / 配饰」。
  ⚠️ 国标 **GB/T 23560-2009《服装分类代码》不适用** —— 它按**生产工艺**分
  （机织 / 针织 / 毛皮皮革 / 特种 / 防护装备），面向生产与统计，不是给人整理衣橱用的。
- **小类**：只建类别、**一个取值都不预置**。切分方式因人而异，预置就是噪音。
  用户加取值时选它属于哪个大类。
- **颜色**：唯一额外预置的一套。色名混乱（「杏 / 米 / 裸」到底哪个），给一套标准词表
  省掉反复改名，前端还能按色名渲染色块（见 `frontend/src/lib/tags.ts` 的 `COLOR_HEX`）。
- **材质 / 风格 / 色系**：只建类别，取值留空。

### 前端约定

- 筛选栏、编辑器、标签管理**共用** `frontend/src/lib/tags.ts` 里的级联规则，不各写一份。
- **勾选子值自动带上父值；取消父值连带取消子值**（`toggleCascaded()`）。这样筛选集合
  永远自洽，不会留下「看不见却生效」的条件。
- 级联子类别按父取值**分组显示**：父级已选 → 只列该父值下的子值（越点越窄）；
  父级未选 → 全部子值分组列出，每组带组名。
- 筛选栏**隐藏没有取值的类别**（空的小类 / 材质不占位置）；编辑器与标签管理里照常显示，
  否则用户没地方加取值。

### 播种时机

- 默认项在**用户创建时**播种（注册、bootstrap 管理员、`cli create-user` 三处）。
  ⚠️ 不要改成「首次访问时懒加载」—— 用户删掉某个默认类别后会被重新塞回来。
- 播种前会检查该 scope 下是否已有类别，所以数据迁移重复执行也安全。
- **新增的类别轴不会自动补**（补了就等于推翻「删了别再塞回来」）。要拉回新默认：

  ```bash
  docker compose exec api ./entrypoint.sh cli reseed-tags --username naonao --yes
  ```

  它会清空该用户的全部标签类别/取值并重建，**衣物本身不动，只解除标签关联**。
  输出会列出每个 scope 的类别与预置取值个数、以及级联关系。
- 类别 / 取值删除时**显式清理关联表**，不依赖数据库级联（SQLite 默认不强制外键）。

### 迁移

`0003_tag_cascade` 加两列自引用外键（SQLite 走 `batch_alter_table` 重建表），
并把既有用户的「小类」挂到同 scope 的「大类」下。历史小类取值一律留 `NULL`（未归类），
不做猜测。`downgrade` 只丢这两列，不动数据。

## 媒体文件（批次 2）

`<img src>` 带不了 `Authorization` 头，所以图片走**签名 URL**：

```
/api/media/<相对路径>?e=<过期时间戳>&s=<HMAC-SHA256(路径 + 过期时间)>
```

- 签名只绑定「路径 + 过期时间」，改动任一项即失效；过期后返回 403。
- 默认 TTL 7 天（`WARDROBE_MEDIA_URL_TTL_SECONDS`），列表接口每次返回新签名的 URL。
- 落盘结构：`<media_root>/<owner_id>/<年月>/<uuid>.<ext>`，原图**不重压**，
  另生成两档 WebP 缩略图（240 / 720 px）。
- 读取时 `resolve_key()` 拦路径穿越；上传时用 Pillow 真解一遍，伪造成图片的文本会被拒。
- 删除衣物 / 图片会连带删除磁盘文件；多文件上传中途失败会回收已落盘的部分。
- **上传大小是三层的，改一层不够**（v1.0.0 修 413 踩过）：
  1. 单张 `WARDROBE_MAX_UPLOAD_BYTES`（默认 20 MB）→ 超了只跳过这一张；
  2. 网关 `client_max_body_size`（镜像内 nginx 与 `.201` 站点配置都是 **64 MB**）
     → 按**单个请求体**算，超了直接 413，请求根本到不了后端；
  3. 前端 `frontend/src/lib/upload.ts` 的 `UPLOAD_BATCH_BYTES`（**24 MiB**）
     → 按字节分批串行发，保证每批都远小于 2。
  改 2 就要同步改 3，否则「一张都传不进去」；只改 1 没有意义（2 先拦）。
  分批时前端传 `start_index`（已建件数），后端据此续编号，避免第二批又从
  `(2)` 开始 —— 不然一整墙衣服会大面积重名。
- ⚠️ **`delete_keys()` 吞掉一切异常**（只记 warning）。数据库事务已经提交，文件删不掉
  只是留垃圾，不该让整个请求 500 —— 用户看到「删不掉」但数据其实已删，比留孤儿文件糟糕。
- ⚠️ 媒体目录**不能**在服务运行时清理（我踩过：清 `backend/e2e-media` 导致所有演示图
  变成死链）。要清就停服务再清。

## ⚠️ `expire_on_commit=False` 的坑（踩过）
`SessionLocal` 用了 `expire_on_commit=False`（async 下避免 commit 后触发懒加载）。
副作用：**commit 之后对象仍带着旧的已加载关系集合，而 `selectinload` 默认不会覆盖
已加载的集合**。表现是「改了标签 / 调了封面顺序，接口返回的还是旧数据」。

- 需要重新读的关系，必须加 `.execution_options(populate_existing=True)`（见
  `routes/garments.py::_load_garment`）。
- 关系上的 `order_by` 也只在首次加载时生效，序列化时显式再排一次更稳。

## 接口一览（批次 2）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/tags/categories?scope=` | 列类别 + 取值（含 `parent_category_id` / `parent_value_id`） |
| POST | `/api/tags/categories` | 新建类别（重名 409，可带 `parent_category_id` 做级联） |
| PATCH/DELETE | `/api/tags/categories/{id}` | 改名 / 改层级 / 删除（连带清关联，子类别降级为顶层） |
| POST | `/api/tags/categories/{id}/values` | 新建取值（重名 409，可带 `parent_value_id`） |
| PATCH/DELETE | `/api/tags/values/{id}` | 改取值 / 改归属 / 删除（自动解除已打标） |
| GET | `/api/garments?q=&tag_value_ids=&page=&page_size=` | 列表，`tag_value_ids` 多值取**交集** |
| POST | `/api/garments` | 新建（可带 `tag_value_ids`） |
| GET/PATCH/DELETE | `/api/garments/{id}` | 详情 / 改 / 删（删则连带清图） |
| POST | `/api/garments/{id}/images` | 多文件上传（字段名 `files`） |
| POST | `/api/garments/{id}/images/{img}/primary` | 设为封面（排到最前） |
| DELETE | `/api/garments/{id}/images/{img}` | 删单张图 + 清文件 |
| GET | `/api/media/{key}?e=&s=` | 签名取图 |

级联相关的 400：父类别跨 scope、父类别本身不是顶层（要三层）、
顶层类别的取值挂父值、父取值不属于该子类别的父类别、带取值的类别再挂父级。

列表返回的 `cover_url` / `thumb_*_url` 都是**已签名的完整路径**，前端直接塞 `<img src>`。

## 已知取舍 / 后续加固

1. **refresh token 放在 localStorage**，理论上可被 XSS 读取。自托管单用户场景可接受。
   上 https 后建议改为 httpOnly + SameSite=Strict 的 Cookie（需同步调整 CORS 与 CSRF 策略）。
2. **X-Forwarded-For 直接信任首段**。仅在反代（Lucky / nginx）可信的前提下成立；
   若 API 直接暴露公网需要收紧。
3. 注册默认关闭。开放注册前应加邮箱验证或邀请码。

## 浏览器验收（agent-browser）

本机 Chrome 不在默认位置，**每条命令都要带**：

```bash
agent-browser open <url> --executable-path "C:/Users/openclaw/AppData/Local/ms-playwright/chromium-1243/chrome-win64/chrome.exe"
```

三个坑：

1. ⚠️ **不要把 `agent-browser` 的输出接进管道**（`| grep` / `| tail`）。daemon 会继承
   管道的写端，管道永远不 EOF，命令就永远不返回 —— 看起来像「冷启动卡死」，其实
   `open` 早就成功了。一律 `> 文件 2>&1`。
2. daemon 可能在两次工具调用之间被回收，页面变回 `about:blank`。所以**整条流程要放在
   同一次 bash 调用里**跑完。
3. 给 daemon 传 `--executable-path` 会提示 `ignored: daemon already running`，属正常。

现成的验收脚本（一次性跑完，截图落到 `out/wardrobe-shots/`）：

```bash
bash out/wardrobe-shots/run.sh    # 缩略图墙 / 筛选 / 标签管理 / 编辑器
bash out/wardrobe-shots/run2.sh   # 真实「新建衣物 + 上传图片」全流程
```

⚠️ 用 `eval` 点击元素时，选择器**必须限定作用域**。例如 `.chip-toggle` 在筛选栏和
编辑弹窗里都存在，`document.querySelectorAll('.chip-toggle')` 会先命中筛选栏那个。

## 批次 3：AI 抠图 + 智能打标

### 架构（DECISIONS D5 / D6）

```
上传衣物 ──► POST /garments/{id}/process（status=pending）
                 │
                 ▼  Worker 轮询（独立进程，共享 DB + 媒体目录）
        rembg 抠图 ──► 产出 kind=cutout 的图（原图保留，不抢封面）
        VLM/CLIP ────► 候选名称 + 标签写入 ai_suggestion
                 │
                 ▼
   needs_review（有产出，等用户确认）／ ready（没东西可看）／ failed（出错，可重试）
                 │
                 ▼  用户在审核界面确认 / 修改
               ready
```

- **API 不装模型**：抠图的 ONNX 只在 Worker 镜像里，API 镜像保持 < 300MB（D5）。
- **队列就是 `garments.status`**：不引 Redis/MQ。Worker 用一条带 WHERE 的 UPDATE
  抢占任务（谁的 rowcount=1 谁抢到），多副本安全。
- **卡死回收**：processing 超过 `WARDROBE_WORKER_STUCK_MINUTES`（默认 30）会被
  退回 pending 重跑，防止 Worker 被 kill 后衣物永远卡住。

### Worker 用法

```bash
# 常驻轮询（docker compose 里的 worker 服务就是这条命令）
python -m app.worker

# 跑一批就退出（测试 / 手工补跑）
python -m app.worker --once --batch 5

# 只处理某一间
python -m app.worker --once --garment-id 7
```

### 配置（全部走 WARDROBE_ 前缀环境变量，默认值都是最保守的）

| 变量 | 默认 | 说明 |
|---|---|---|
| `WARDROBE_AI_MATTING_PROVIDER` | `none` | 抠图：`none` / `rembg` |
| `WARDROBE_AI_TAGGER_PROVIDER` | `none` | 打标：`none` / `clip`。**批次 6 起不再有 `vlm` 这一档** —— 视觉模型改成按用户配置（见下） |
| `WARDROBE_MATTING_MODEL` | `u2net` | rembg 模型名。小机器/离线环境建议 `u2netp`（4.7MB，实测单张 0.6-0.7s） |
| `WARDROBE_WORKER_POLL_SECONDS` | `2.0` | 队列空时的休眠 |
| `WARDROBE_WORKER_BATCH_SIZE` | `2` | 一轮最多处理几件 |
| `WARDROBE_WORKER_STUCK_MINUTES` | `30` | processing 超时回收 |
| `WARDROBE_AI_INPUT_MAX_EDGE` | `1600` | **抠图前**把图缩到这个长边。手机原图 15 MP 直接喂 rembg 会按原尺寸跑 alpha matting，内存/耗时超线性，能把整台机器拖死（2026-10-17 事故）。设 0 = 不缩放（不推荐） |
| `WARDROBE_WORKER_MEM_LIMIT` | `1500m` | **worker 容器内存硬上限**（compose 的 `mem_limit` 读它）。超了只 OOM 掉 worker 并自动重启，宿主机不受影响 |
| `WARDROBE_WORKER_JOB_TIMEOUT_SECONDS` | `600` | 单件处理硬超时 |
| `WARDROBE_WORKER_HARD_EXIT_ON_TIMEOUT` | `true` | 超时后主动退出进程（退出码 75）让容器重启。推理线程取消不掉，不退出会一直吃 CPU + 内存 |
| `WARDROBE_VLM_BASE_URL` / `_API_KEY` / `_MODEL` | 空 | **不再自动生效**（批次 6 起按用户配置）。仅作运维批量预填用：`python -m app.cli seed-llm --username <名字>` 把这三项写进指定用户 |
| `WARDROBE_CLIP_MODEL` / `_PRETRAINED` / `_THRESHOLD` | ViT-B-32 / laion2b / 0.18 | CLIP 兜底，需额外装 torch + open_clip，全局单例（无地址与 Key，属「机器上装没装」而不是「谁的配置」） |
| `WARDROBE_WORKER_REFINE_PORT` | `8001` | Worker 内部 HTTP 端口，只服务**框选重抠**。只监听容器网络（compose 没有 publish）；`0` = 关掉，框选重抠会提示不可用 |
| `WARDROBE_WORKER_REFINE_URL` | 空 | API 侧用它把重抠转给 Worker（compose 里已写成 `http://worker:8001`）。**留空 = 在 API 进程里算**，只有装了 rembg 的裸机才有效 |

### 框选重抠为什么绕一圈：API 镜像里没有 rembg

`POST /garments/{id}/images/{image_id}/matte-box` 是**同步**接口（框一块、点一下、
马上要看结果），天然落在 API 进程里。但抠图模型只装在 Worker 镜像里（D5：API 保持
轻量）。这两件事凑一起的结果是：Docker 部署里这个功能**从来就没成功过**，稳定报

```
rembg 不可用：No module named 'rembg'
```

而裸机（201）把两套依赖装在一个 venv 里，所以本地怎么点都好使 —— **测不出来的那种坑**。

现在的走法（`app/services/refine.py` → `app/worker/refine_api.py`）：

```
浏览器 ──► API  matte-box 路由
              ├─ 配了 WARDROBE_WORKER_REFINE_URL ─► POST worker:8001/refine/matte-box
              │     只传两个 storage_key（两边共用 ./data/media，不搬图片），
              │     Worker 用自己的模型算完把 PNG 原样回传
              └─ 没配 ─► 在本进程里算（裸机 / 本机开发）
```

几个刻意的选择：

- **不给 API 装 rembg**：那会让入口容器多背 180MB 模型 + ORT 运行时，一次重抠就
  加载，OOM 一次整个网站都挂。
- **只传 key 不传图**：`./data/media` 是共享挂载，让 Worker 自己读盘。
- **落库与落盘留在 API**：Worker 只负责「算」，返回 PNG；DB 记录和文件替换仍由 API
  做，算失败也写不坏数据。
- **跑在 `_AI_POOL` 里**：和后台流水线共用那个只有 1 个线程的池子，同一时刻只有一次
  推理 —— 1~4 核的机器上并行只会一起变慢、一起吃内存。
- **crop 也要缩**：框可以一下框住整张 15 MP 原图，送模型前同样按
  `WARDROBE_AI_INPUT_MAX_EDGE` 缩，掩码再按原始裁切尺寸拉回来。

Worker 那边用 `uvicorn` 在**后台线程**里起（`refine_api.start_refine_server`）。
不跟主循环共用一个事件循环，是因为 uvicorn 会去装自己的 SIGTERM 处理器，
把 worker「跑完手上这批再退」的逻辑顶掉；在非主线程里它会自动跳过（uvicorn 自己
判断的），主线程的信号处理原封不动。

#### 一个容易被当成「卡死」的坑：numba 编译缓存

`rembg` → `pymatting` 的 `kdtree.py` 里有 `@njit(..., cache=True, parallel=True)`。
`import rembg` 会**当场编译**它（LLVM），在 1 vCPU 的 J1800 上要 **5 分钟以上**，
期间第一次抠图 / 框选重抠全在干等 —— 日志里一行都没有，看起来就像卡死。

裸机上不明显：venv 的 `site-packages` 可写，numba 把编译产物缓存进去，第二次起只要几秒
（这就是开发机上「`import rembg` 只要 7s」的原因）。**容器里镜像层是只读的**，
缓存写不进去 → 每次启动都重编译一遍。

修法：compose 里给 worker 两个设置

```yaml
environment:
  NUMBA_CACHE_DIR: /data/numba
volumes:
  - ./data/numba:/data/numba
```

缓存随部署目录保留，重启 worker 只需几秒。删掉 `./data/numba` 只会让下次启动变慢。
冒烟 9h 会先烤热再验一次（首次 vs 第二次的耗时对比），缓存失效会直接 FAIL。


### 时间列的时区语义（踩过一次，代价很大）

`garments.processed_at` 建表时是 `DateTime`（= `timestamp without time zone`），**只能写
naive UTC**，用 `app/core/time.now_naive_utc()`；而 `created_at` / `updated_at` 来自
`TimestampMixin`，是 `timestamptz`，**必须写 aware**。

混用的后果不是「时间差 8 小时」这种小问题：asyncpg 对无时区列拒绝 aware 值，直接抛
`DataError: can't subtract offset-naive and offset-aware datetimes`。2026-10-17 的事故里，
它是从 `_fail()` 里冒出去的 —— 于是「把衣物判死」这一步本身写不进库，这件衣物永远停在
`processing`，前端一直显示「处理中」。

★ **SQLite 不校验时区**，本地测试全绿也拦不住。改这类代码时，一定要在 PG 上验一次
（`smoke_release.sh` 的 9f 就是干这个的）。

### 打标的两条铁律

1. **只从用户自己的标签里挑**：候选池就是该用户的 garment 标签取值（小类会带上
   父取值，如「外套/风衣」），模型没机会发明用户不存在的标签。
2. **VLM 必须回 JSON**：解析不出 JSON、给出了候选之外的词，一律当作没建议处理，
   绝不把模型的自由发挥写进数据库。

### 模型要求：必须是「视觉模型」

打标要把图片交给模型**看**，所以只有多模态（Vision）模型能用 —— 纯文本模型填了也用不了。
这一条写进了设置页与管理员代设处的界面说明（`.hint-block`），用户不必翻文档。

- **传图方式**：OpenAI 兼容的 `image_url` + base64 data URI（`data:image/jpeg;base64,…`，
  JPEG q88），所以服务端要支持这种**内联图片**；`base_url` 填到 `/v4`、`/v1` 这一层，
  程序自己拼 `/chat/completions`（带上就成了 `/chat/completions/chat/completions`）
- **可用示例**：CT202 实测用的是**智谱 `glm-4v-flash`**
  （`https://open.bigmodel.cn/api/paas/v4`）；`qwen-vl-max`、`gpt-4o-mini` 这类
  OpenAI 兼容的视觉模型同样可用。纯文本模型如 `glm-4-flash`、`deepseek-chat` 不行
- **输出契约**：只认 JSON（`{"name":…, "tags":[…], "confidence":…}`）。`glm-4v-flash`
  这类小模型常写出**缺逗号**的数组（`["鞋子" "黑"]`），`VlmTagger._loads()` 会先修中文
  引号、再补缺失的逗号 / 去掉尾随逗号 —— 不修就整条建议作废，白白丢掉名字和标签
- **报错要带上游的原因**（`VlmTagger._http_error`，折成一行、截断 200 字符）：
  `model not found` = 模型名写错、`invalid content type` = 填了不看图的纯文本模型、
  `invalid api key` / `insufficient balance` 同理。只回一个光秃秃的 `400`
  等于把排查成本丢给用户；这些原因会一路显示到「待确认」的提示里

### 降级矩阵（DECISIONS D7 的落地）

| 场景 | 行为 |
|---|---|
| rembg 没装 / 模型加载失败 | 只跳过抠图，照常打标；都没有就直接 ready |
| VLM 没配 key / 超时 / 返回垃圾 | 当作没建议；有抠图产出就进 needs_review |
| 全部报错且无产出 | failed，原因写在 `ai_suggestion.error`，可重新入队重试 |
| 处理中进程被杀 | 超过 stuck 分钟数自动回 pending |

### CT202 实测记录（2026-10-14）

- 环境：Debian 12 / Python 3.11.2 / 2C4G，rembg 2.0.60 + onnxruntime 1.31.0（清华源安装）。
- `u2netp` 模型加载 0.08s，单张 900×1200 抠图 **0.6-0.7s**，输出 RGBA，

### 复核弹窗的按钮语义：谁是中间步骤、谁才是终点

`ReviewDialog` 有两个回调，**别接错**：

| 回调 | 语义 | 谁在用 |
|---|---|---|
| `onUpdated(g)` | 只把最新衣物同步给列表，**不关弹窗** | 「修整抠图」保存完、**「用抠图做封面」** |
| `onDone(g)` | 复核**结束**，关弹窗 | 「采纳并入库」「重新处理」 |

- **「用抠图做封面」是复核里的一步，不是终点** —— 设完封面弹窗留着、按钮变「已是封面」，
  接着改名字/标签，最后点「采纳并入库」一次结束。
  早期这里接的是 `onDone`：点一下弹窗就没了，名称/标签没被采纳、状态仍是 `needs_review`，
  卡片上还挂着「复核 AI 结果」，再点又回到同一个 AI 建议页 —— 看着就像「点了封面却被退回
  AI 建议」，而且关窗后再也没法点「采纳并入库」，一次操作被劈成两趟。
- 与衣物编辑弹窗里的「设封面」（`GarmentEditor` 的 `imageAction`）**行为一致**：
  同一个语义在两处不该有两种行为。
- 判定标准很简单：**这个动作结束后，用户还需要在这个弹窗里继续做事吗？** 需要 → `onUpdated`。

## 批次 4/5/6：套装搭配（拼图编辑器）

### 数据模型

```
outfits ──┬── outfit_items     摆位（一层一件）
          ├── outfit_images    成图 kind=result / 用户上传 kind=upload
          └── outfit_tags      搭配标签（scope=outfit 的那套体系）
```

- `outfit_items` 存**归一化坐标**：`x` / `y` 是图层中心在画布里的比例（0~1），
  `w_ratio` 是图层宽占画布宽的比例，`rotation` / `flip_h` / `opacity` / `sort_order`
  各管一摊。`garment_id` 与 `garment_image_id` 都是 `SET NULL` —— 衣物删了，
  搭配里留一条占位（前端显示「素材已删除」），不会把整套搭配带崩。
- 画布固定 3:4，导出 `EXPORT_W/EXPORT_H = 900/1200`。图层在画布里的**归一化高度**
  = `(w_ratio / 宽高比) × (EXPORT_W / EXPORT_H)`，前端 `boxSize()` 与导出 `render()`
  共用这一口径，保证所见即所得。

### 素材裁边（把大片空气切掉）

抠图是「原图尺寸 + 透明底」，主体常只占中间一小块。进画布前先量一遍：

1. 缩到 512 长边的探针图，扫 alpha 找主体外框（阈值 `ALPHA_MIN = 4`，压得很低，
   免得把衣服的软边一起裁掉）；
2. 整张都不透明（没 alpha 的原图）时，改削四周「整行/整列 ≥99.5% 纯白」的边，
   每边最多削 1/4 —— 白衬衫这类主体本身是白的图，不至于把衣服也啃掉一块；
3. 外框四周留 1% 余量，按 `floor/ceil` 映射回原图坐标（宁可多留边）。

> **坑（批次 6 修的）**：`.olayer img` 必须是 `position: absolute`。裁边是靠 inline 的
> `left/top` 把原图挪出可视窗、只露中间那块（`.olayer-img` 是 `overflow:hidden` +
> `aspect-ratio`）。img 默认 `static` 时 `left/top` **会被静默忽略**，画布上露出来的是
> 原图左上角 —— 用户看到的就是「衣服缺了一块」，而成图走 `drawImage(src…)` 取源矩形，
> 反而是对的，于是「编辑器里被切、存下来正常」的诡异现象。
> 回归脚本 `outfit_wysiwyg.js` 用像素外框把这条钉死（比对「画布上露出的像素」与
> 「源图按裁边窗口取出的那块」，偏差 ≤ 0.7%）。

### 自动排版（新加的图层摆哪）

新图层默认**按格子缩到装得下**，而不是固定 `w=0.45`（细长裙子换算成高度会超过整个
画布，一加进来就被画布边缘切掉一截）。一件居中占满，多件按 2 列铺格子
（细长的裙子靠高度吃尺寸，两列比两行更能用满画布）：

- `autoCell(i, n)` 给第 i / n 件的格子中心与格子尺寸，`cellWidth()` 按宽高比算格子内
  最大可用宽度，四周留 10%（`CELL_FILL = 0.9`）；
- 只有**用户还没手动动过**的图层（`auto` 标记）会被重新排；拖过/缩过的图层原地不动；
- 裁边量出来才知道真实宽高比，所以量完会按裁后比例重新适配一次。
- 图层被拖到露在画布外时，右栏给一条 `53% 露在画布外（会被切掉）` 的提示，
  配一个「适应画布」一键收回。

### 编辑区画布大小

- 自适应：`width = min(100%, (92vh − 180px) × 0.75)`，高度按 3:4 反推 ——
  1440×900 下是 486×648（占屏高 72%），一屏放得下不翻页；
- 用户可调：工具栏「画布大小」滑杆（60%~160%，存 localStorage），
  CSS 变量 `--ocanvas-zoom` 乘在自适应宽度上，`自适应` 按钮一键回 1；
- 右栏（名称/标签/图层/图层微调）高度封在 `calc(92vh − 158px)` 以内并自己滚，
  内容再多也不把弹窗顶高；图层微调（缩放/旋转/透明/镜像/适应画布/复位）放在
  图层列表下面，不占画布高度。

### 成图与卡片

保存时把图层画到离屏 canvas 合成成图（`render()`），再按**内容框**（`contentBox()`，
各图层外接框 + 2% 余量）裁到长边 1200、最多放大 2 倍 —— 库里存的不是整张空画布，
卡片的示意图/缩略图才是「有内容的」。卡片封面用 `object-fit: contain`，
底色接着卡片背景，看不出接缝。

### 接口一览（批次 4~6）

| GET | `/api/outfits` | 列表（含封面图、标签） |

## 批次 7：上身图（可选）

> 「摆的是怎么搭，穿上是穿上去什么样」—— 搭配本身已经能表达前者，上身图只是额外记一笔，
> **可以一张都不传**。

### 数据模型：没新增表，只是多了一个 kind

`outfit_images.kind` 现在有两类：

| kind | 含义 | 数量 |
|---|---|---|
| `result` | 编辑器保存时合成的**搭配图** | 只留最新一张，`sort_order=0` |
| `worn` | **上身图**（真人穿搭照） | 可多张，上限 12 张 |

- 早期的 `upload` 别名与 `worn` 同义，写入时归一成 `worn`（老客户端不会写出第三种类别）；
  读的时候两种都认（前端 `isWornImage()`）。**不需要迁移**：`kind` 本来就是 String(16)。
- 排序即「卡片默认显示哪张」：`sort_order` 最小的那张就是封面（`cover_url`）。
  `result` 固定 0，所以**有上身图也不会把搭配图顶掉**；想让某张上身图当封面，
  走 `/images/{id}/primary` 把它压到最前面即可。
- 删光上身图完全不影响这套搭配：搭配图、封面、图层都还在。

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/outfits/{id}/images`（`kind=worn`） | 传上身图；超过 12 张返回 400 |
| DELETE | `/api/outfits/{id}/images/{image_id}` | 删任意一张（搭配图 / 上身图同一条路） |
| POST | `/api/outfits/{id}/images/{image_id}/primary` | 设为卡片默认显示的那张 |
| GET | `/api/outfits` | 列表带全部 `images`（含 kind），前端据此挑「搭配图 / 上身图」 |

> 上限是**先数再存文件**的：被拒的那张不会在磁盘上留下没人认领的图。

AI 推荐取图的优先级也顺势理顺：**现场画布 → 库里搭配图 → 上身图**
（画布还空着、只传了上衣照时，总比没图可看强）。

### 界面

- **编辑器右栏最下面**：「上身图（可选 · 想记录实际穿上的样子就传）」。
  缩略图用 `object-fit: contain`（复核「传了什么」，整张看得全比铺满重要）、
  每张右上角 ✕ 删除、点开走大图；一张都没有时只留一句「不传也完全没问题」。

## 批次 8：抠图精修支持缩放 / 平移

> 修边的活儿最后都落在「这一个像素」上。整图缩进一屏时最小的一笔也有好几个像素宽，
> 领口那条一两像素的白边根本点不准 —— 所以编辑器得能放大，而且放大后笔尖要落在
> **你想要的那个图像像素**上。

### 五种手段（`CutoutEditor.tsx`）

| 工具 | 干什么 | 关键实现 |
|---|---|---|
| 擦除笔 | 抹掉残留（衣架、吊牌、背景碎片） | 把 `alpha` 置 0 |
| 恢复笔 | 把**原图**的像素整块贴回来 | 颜色与不透明度都取自原图；抠图边缘被 alpha matting 带偏过，沿用抠图只会把错色补回去。整笔范围内一个不透明像素都没有时**不动笔**，免得一挥把半张背景墙补回来 |
| 框选重抠 | 框一块丢回模型重跑 | `POST /garments/{id}/images/{image_id}/matte-box`，crop 后分辨率更高、背景更单纯，比整图重跑准 |
| **抓手** | 选中后左键直接拖画面 | 最像常识的平移入口，不用先读说明。`cursor: grab`（拖动中 `grabbing`） |
| 缩放 / 平移 | 放大了贴着边缘修 | 见下 |

撤销 / 重做走**笔画重放**（只记「哪些点、什么模式、多大笔刷」，从基线重建后重放），
不是像素快照 —— 快照要存 12 份全图，手机上就得几百 MB。

### 视口：为什么不用 `transform: scale()`

舞台 `.refine-stage` 是**取景框**（`overflow: hidden`，高度由弹窗纵向 flex 分配，
见下方「版面预算」），里面一层 `.refine-view` 是「照片本身」：

```
.refine-stage  ── 取景框（固定高度、裁切、接收所有指针事件）
  └ .refine-view  ── 照片：width/height 按「画布尺寸 × 像素比」显式写 px，
      │              transform: translate(pan) 只负责平移；棋盘格画在这一层
      ├ canvas.refine-canvas   （宽高 100%，位图 = 原分辨率，最长边上限 2200）
      └ .refine-box            （框选框，按**百分比**定位）
```

**不用 `transform: scale()` 的原因**：里面那个框选框是按百分比定位的，transform 的
百分比基准不会跟着缩放变，得另外换算一遍。直接改宽高，框的百分比天然就是相对
「照片」的，代码里只剩「照片多大」一件事。

**缩放口径是像素比**：`100% = 一个图像像素对一个屏幕像素`（1:1），适应窗口时通常
只有 20%~30%。滑杆、百分比、笔刷光圈共用这一把尺子，不用「相对适应窗口的倍数」——
那样拖到 100% 反而不是 1:1，修边时容易看错。范围 `[适应窗口, min(8, max(2, 适应×8))]`：
大图别放到离谱，小图（本身不到 500px）也能放到 800% 看织纹。

**以光标为锚点缩放**（`zoomAt`）：`view` 居中后再沿 `pan` 推开，于是

```
屏幕上 = 取景框中心 + pan + (锚点在照片里的比例 − 0.5) × 显示尺寸
```

缩放前后各写一次、令两式相等，解出新 `pan`；锚点底下那个像素就钉在原地。

**平移边界**：`|照片 − 取景框| / 2`。

> **坑**：一开始写成 `max(0, 差/2)`（也就是「比取景框小的那条轴锁在正中」），
> 结果光标缩放到一半横向拖不动 —— 锚点被强行拉回中心，看着就是「缩放会漂」。
> 换成 `|差|/2` 后两种情形统一：图大能拖到边缘对齐，图小只能在框内挪（也不会走丢）。

**手势**：**滚轮**以光标为锚点缩放（`Shift + 滚轮`放行给浏览器滚弹窗 —— 早期实现是
「普通滚轮不拦、必须 `Ctrl` 才缩放」，但那样鼠标一停在画布上就滚不动页面、又要用户
先知道得按 `Ctrl`，等于没有入口）；**抓手工具**或按住**空格** / **鼠标中键**拖动画面；
**方向键**微调平移（`Shift` 加速到 120px/步，贴边修的时候比拖鼠标稳）；触屏**双指**捏合缩放 +
平移（捏合中点位移顺带就是平移）。指针事件全部挂在**舞台**上（原来挂在画布上），
这样在留白处也能起手拖动，笔迹坐标仍按画布矩形换算。

> **为什么一开始「一放大就只剩中心点」**：`+` / `−` / 滑杆（以及当时的滚轮）都把新比例
> 套在**舞台正中**，放大后要修的地方早被推出画面；而平移只有空格拖 / 中键拖两种，
> 又只写在底部提示文字里。修法是两条一起：**缩放锚点改成「鼠标最后停留的位置」**
> （`lastAnchorRef`，由 `onPointerMove` 维护，鼠标没进过画面才回落到中心），
> 再加**抓手工具 / 导航器 / 方向键**三个显式入口。

**导航器（左上角小地图）**：只在「放大到看不全」时出现（`scale > fitScale`），
显示整张图缩略 + 当前视口方框；点哪儿跳哪儿，也可以拖方框扫。回答「我现在看的是整张图的
哪个位置」。缩略图在每次 `paint` 之后重画，擦掉的部分在缩略图里也看得出是透明。

> **坑（三个，都是验收里量出来的）**：
> ① **别放右下角** —— 短视口下 `.modal-body` 溢出，舞台底部被弹窗 footer（取消 / 保存修整结果）
> 盖住，导航器右下角 `elementFromPoint` 命中的是「保存修整结果」，点一下弹窗直接关了。
> ② **缩略图空白** —— 画布尺寸 effect 依赖漏了 `showNav`：适应窗口时导航器根本没渲染
> （`navCanvasRef.current === null`），放大后才挂上、effect 不重跑，画布停在 0×0。
> ③ **`drawNav` 必须定义在 `paint` 之前**（`paint` 要调它），否则 TS2448 / TS2454。

**笔刷光圈**：原来是个固定的 26px 圆形光标，笔刷调到 120 也不变，看不出会涂到哪儿。
现在按「笔刷像素 × 像素比」实时画圈（擦除红、恢复绿），放得越大圈越大。

> **坑**：浏览器给**滚轮事件**的 `clientX/Y` 是**整数**（真实鼠标位置本来也是整数）。
> 所以锚点要按上报的坐标算；拿 `getBoundingClientRect` 里的小数位置去推期望值，
> 会看到每步约 1px 的「假漂移」，其实底层像素钉得死死的。

### 版面预算

| 位置 | 值 | 为什么 |
|---|---|---|
| `.modal-refine` | `height: min(calc(95vh - 24px), 880px)` | 默认 90vh 在 1366×768 上要翻页；**必须有确定高度**，否则里面 `flex: 1` 分不到空间（见下） |
| `.modal-refine .modal-body` | 纵向 flex + `flex: 1 1 auto` | 让取景框**吃掉剩余高度**，而不是把 body 顶出滚动条 |
| `.refine-stage` | `flex: 1 1 0; height: auto; min-height: 170px` | 高屏舞台更大，短屏收到 min-height，body 不溢出。实测 1280×900 → **491px**，1262×568 → 176px 且溢出 0 |
| `≤640px` | 取景框 `clamp(190px,42vh,440px)`，滑杆收窄、`1:1` 收起 | 手机窄，说明文字多折两行，把高度让给取景框 |

> **坑**：`.modal` 只有 `max-height`、**没有确定高度**时，`.modal-body` 的高度仍由内容决定 ——
> 里面再 `flex` 也**没有多余空间可分**，取景框会永远卡在 `min-height`（170px）。
> `max-height` 不产生确定高度。见 `KNOWN_TRAPS.md` 第 17 条。

### 1. 删除级联提示（评估报告 #4）

`outfit_items.garment_id` 是 `ON DELETE SET NULL`，所以删一件衣物**不会**连带删掉
用到它的搭配 —— 那几层退化成「素材已删除」，层上的 `name_snapshot` 还留着衣物名。
这是刻意的保守选择：搭配是用户一层层摆出来的成果，清理衣橱不该顺手把它带走。

但用户得**知道**自己正在影响什么，于是删之前先问一次：

- `GET /api/outfits/referencing?garment_ids=1&garment_ids=2` —— 一次问一批。
  批量删除时若为选中的 200 件各发一次请求，页面会瞬间打出 200 个请求。
  （旧的 `garment_id=` 仍兼容；`layers` 是这些衣物在该搭配里的层数之和。）
- `DELETE /api/garments/{id}?cascade_outfits=true` 与
  `POST /api/garments/batch/delete` 的 `cascade_outfits` 字段 —— 让用户主动选择
  「连搭配一起删」。默认 `false`。
- 两者返回同一组字段：`affected_outfits[]` / `orphaned_layers` / `deleted_outfits`，
  前端删完据此说一句人话（「2 套搭配里 3 层变成空位」）。

> **坑（顺序）**：`_affected_outfits()` 必须在**执行 `db.delete()` 之前**调用。
> session 是 autobegin 的，删完再跑 SELECT 会先 autoflush 掉 DELETE 语句，
> 届时外键已经把 `garment_id` 置成 NULL —— 查出来是空列表，提示永远为「无引用」。
> 批量删除里尤其容易写反（我先写成了「先删完再汇总」）。

前端 `ConfirmDeleteDialog.tsx`：打开即查引用，列出搭配名与层数（超过 5 套折叠），
勾选框的**文案随勾选状态改变**（`不勾选则只删衣物：…… 层会变成「素材已删除」`
↔ `这些搭配和它们的成图会一起删掉`），主按钮也跟着变
（`确认删除` ↔ `删除衣物和搭配`）。批量删除复用同一个组件，单件 / 多件只在标题与
调用哪个接口上分叉。

`useState` + 提前 return 分支，同一套结构抄五遍；换成 `if (!(await confirmDialog({...}))) return;`
每处只改一行，样式与层级集中在一处管。

`index.html` 里的一段内联脚本在**首帧之前**把选择解析成具体的 `data-theme` 写到
`<html>` 上，CSS 就只需要一个属性选择器 —— 既不用维护两份相同的深色调色板，
也不会先闪一下浅色。`src/lib/theme.ts` 负责后续的系统切换与持久化，

### 3. 修掉四个真 bug

**① `.badge` 被两条规则打架。** 状态角标那条写成了裸 `.badge { position: absolute; }`，
把批次 2 就存在的通用 `.badge`（列表里的 inline 小标签）一并变成了绝对定位。
「设置」页的「管理员」徽章没有任何定位祖先，于是飞到了视口左上角 —— 一直如此，
只是没人盯着那个角落看。修法是把角标规则收窄成 `.gcard-thumb .badge`，
并在验证脚本里钉一条「徽章必须在卡片内」。

**② `delete_keys` 吞不下 `SystemExit`。** 这个坑以前踩过一次（当时把裸 `unlink()`
改成 `try/except Exception`），这次又换个姿势踩回来：执行环境的文件安全钩子
（删除重定向到回收站、批量删除守卫）拦下删除时是 **`raise SystemExit(1)`** ——
`SystemExit` 继承 `BaseException` 而不是 `Exception`，`except Exception` 接不住。
后果是：数据库事务**已经提交**、衣物确实删掉了，但请求返回 500。

- 复现：连续 15 轮「造 2 件带图衣物 + 1 套搭配 → 批量删除」，
  第 6 轮起必挂（守卫按删除**次数**累计触发）。
- 修法：`DELETION_SWALLOWED = (Exception, SystemExit)`，只放过 `SystemExit`，
  `KeyboardInterrupt` 之类照常上抛。`pipeline.py` 里那处清理旧抠图的 `unlink` 同样处理。
- 这个失败只出现在带安全钩子的执行环境里（CT202 的裸 Linux 不会），
  但「删个缓存文件没删掉」把已成功的请求变成 500 无论如何都是错的。

**③ `<ConfirmHost />` 排在了 `<Routes>` 前面 —— 确认框被自己的弹窗盖住。**
所有 `.overlay` 都是 `z-index: 50`，层级由 DOM 顺序决定：确认框的宿主必须排在路由**之后**。
排在前面时，「编辑衣物弹窗里弹删除确认」这一路会被编辑弹窗盖住。
这个 bug 特别阴 —— `count()` 是 2、`isVisible()` 是 `true`、按钮状态是
`visible, enabled and stable`，静态断言全过；只有 Playwright 真去点时才报
`… <button class="chip chip-toggle">短裤</button> … intercepts pointer events`。
修完在验证脚本里补了一条硬断言：**按钮中心点 `elementFromPoint` 回来的必须是它自己那层弹窗**。

**④ `Esc` 一次关掉两层弹窗。** `Dialog` 给每个实例都挂了 `keydown`，弹窗一套弹窗，
按一次 Esc 会把确认框和它下面的编辑弹窗同时关掉 —— 用户只想撤销一次删除，结果连编辑器都没了。
改成只有**最上面那层**（`.overlay` 里的最后一个）响应 Esc。

> 这两个都是「换成 Promise 版确认框」才暴露出来的：原来的 `ConfirmDeleteDialog` 只用在
> 衣物列表页（页面本身不是弹窗），既不会嵌套也不会盖住别人。加了 5 个调用点，
> 其中 3 个在弹窗内部，才把层级和 Esc 的问题逼出来。

## 后续优化：素材库等高校准 + 标签筛选（2026-10-16）

批次 5 交付后用户提了两件事：① 搭配编辑器里的素材库有明显白边，显示高度应与画布等高
（电脑浏览器端）；② 素材库支持按标签筛选，放一个筛选按钮然后弹窗。

### 1. 先量，再改

「白边」不是一个可以直接下判断的现象（可能是左栏留白、也可能是缩略图的白底），
所以先写了个临时探针（Playwright 打开编辑器 → 量三栏几何）把数字摆出来：

| 元素 | 高度 |
|---|---|
| 画布那一栏（工具栏 + 画布） | **678px** |
| 右栏（属性 + 图层） | 583px |
| **左栏（素材库）** | **475px** ← 底下一整块白 |

画布高 648px，左栏 475px，`678 - 475 = 203px` 的空白就是白边。顺带看出左栏
`.olib-grid` 的 `max-height: 46vh`（414px）是硬顶，18 件素材里有 9 行，只看得见 3 行。

### 2. 等高：三栏拉伸 + 网格吃掉剩余高度

```css
.oeditor { align-items: stretch; }        /* 行高由画布那一栏决定，左栏拉到同高 */
.oeditor-lib { display: flex; flex-direction: column; min-height: 0; }
.oeditor-lib .olib-grid { flex: 1 1 0; min-height: 0; max-height: none; }
```

行高永远由画布那一栏决定（它的高 = `(92vh - 180px) + 工具栏`，比右栏的
`max-height: calc(92vh - 158px)` 恒定大 8px）。

> **坑 1 —— `flex-basis` 必须是 0，不能是 `auto`。**
> `flex: 1 1 auto` 时，网格会拿**内容高度**（18 件素材 = 1362px）去参与父级的固有高度
> 计算，于是左栏自报 1429px、整行被顶爆、弹窗长到 831px 还溢出。行高从 678 变 1429。
> `flex-basis: 0` 之后左栏的固有高度只剩标题那一行，实测行高回到 678、底边与画布齐平。

> **坑 2 —— 网格容器一旦有确定高度，行轨会被压扁。**
> `.olib-cell` 是 `overflow: hidden`（圆角与角标要裁剪），而「自动最小尺寸」在
> `overflow != visible` 时按 0 算。于是行轨的 base size 为 0、剩余空间又是负数，
> 网格直接把 9 行压成 61px 去凑 611px 的容器 —— 图片 119px 溢出卡片被裁，
> 卡片只剩一个「未抠图」标签。**`scrollHeight` 也等于 `clientHeight`**，
> 看起来「没有溢出」，很能骗过肉眼和断言。
> 改 `grid-auto-rows: max-content` + `align-content: start`：行高只按内容算，
> 溢出的部分交给 `overflow-y: auto` 滚。

手机上三栏变单列，等高没有意义，媒体查询里把网格撤回 `flex: none` + `max-height: 32vh`。

### 3. 标签筛选：一个类别 = 一个维度

`LibraryFilterDialog.tsx` + `lib/tags.ts` 的 `buildFacetGroups(categories, selected)`：
界面里只有一池子勾中的取值 id，维度得在这里补回来 —— **一个类别 = 一个维度**
（类别内选中的取值互为「或」，类别之间取「且」），再交给既有的 `buildTagGroups` 摊平成
后端要的 `tag_groups`。

不做「大类 + 小类算同一个维度」的合并：服务端把分类拆成了两个类别，但它们各自是
一套独立标签（衣物可以只打大类、不打小类），当两个维度取交集才是对的。

**只列有衣物在用的标签**（类别与取值都按 `usage_count > 0` 过滤）。这一条同时解决两个问题：

- 摆出用不到的取值 = 摆一堆必然筛出空结果的按钮；
- dev 库里其实躺着**两套同名类别**（`[8]大类/[9]小类 parent=8/[10]颜色` 是用量为 0 的旧分类树，
  `[15]/[16]/[17]` 才是在用的新树——`migrate_tags.py` 迁移后旧树没删干净），
  按用量过滤天然把旧树挡在门外，弹窗里不会出现两个「颜色」。
  CT202 侧是干净的一套，同一份断言两边都过。

### 4. 顺手修的两处

1. `className="btn primary"` 用的是不存在的 `.primary`（真实类名 `.btn-primary`），
   「保存搭配」「新建搭配」一直渲染成普通按钮 —— 三处一并改正。
2. 「仅显示前 60 件（共 N 件）」的触发条件原来比的是「命中数 > 列表长度」，而没图片的
   衣物本来就会被过滤掉，于是 19 命中 / 18 列表也会报「被截断」。改成只有命中数真的
   超过一页上限（`libTotal > LIB_PAGE_SIZE`）才提示 —— 这处是看 CT202 截图发现的。

## 批次 6：多用户与管理员（2026-10-16）

管理员 / 普通用户两级角色，配套注册三模式、按人配额、按人配置大模型。

### 1. 角色与「别把自己锁在门外」

`users.is_admin`；`app/core/deps.py` 里 `AdminUser = Annotated[User, Depends(get_admin_user)]`，
非管理员一律 **403**（不是 404 —— 不必藏「这里有管理接口」）。

`app/api/routes/admin.py` 全是管理员端点，其中三条保护写死在服务端：

| 保护 | 为什么 |
|---|---|
| 不能删自己 / 停用自己 / 取消自己的管理员 | 误操作一次就再也进不去了 |
| 不能取消最后一个管理员（删号 / 降级 / 停用三条路都拦） | 系统里没有管理员时，注册模式、配额、别人的密码就再也改不动了，只能进容器敲 CLI |
| **管理员不受配额限制** | 否则管理员把标签配额调成 0 就把自己锁在门外，谁也改不回来 |

删号连带清掉衣物 / 搭配 / 标签 / 会话（外键 `ON DELETE CASCADE`）与**媒体文件**：
先把文件的 key 收集起来，`commit()` 之后再 `delete_keys()` —— 库里先干净、磁盘后动手，
顺序反了会留下「库里没有、盘上还在」的孤儿。

### 2. 注册模式为什么进库

`Settings.allow_registration` 来自环境变量，进程启动读一次就固定 —— 而「注册模式」是
管理员随时要改的东西。所以落到 `app_settings` 单行表（`id=1` 固定主键），
环境变量退化成**首次读设置时的初始值**（`services/system.py:_initial_mode()`）：

- 迁移 `0006_admin` **故意不给 `app_settings` 插行**：插一行会钉死初始模式，
  让 `WARDROBE_ALLOW_REGISTRATION=true` 的既有部署静默失去注册入口
- `get_app_settings()` 是「缺行就补」，补行时用 `IntegrityError` 兜底并发（两个请求同时补）

登录页要在**拿到令牌之前**就知道该不该显示注册入口，所以单开了一个不带鉴权的
`GET /api/auth/registration`（`/meta` 是要登录的）。它只暴露模式，不暴露邀请码本身。

### 3. 邀请码的两个细节

```python
_ALPHABET = "ABCDEFGHJKMNPQRSTUVWXYZ23456789"   # 去掉 0/O/1/I/L
```

- **归一化**：去空格、转大写、补回中间那个短横。用户抄码时可能漏短横、写小写、
  前后带空格，都该当成同一个码
- **占用必须原子**（`services/system.py:consume_code`）：

```python
upd = update(InviteCode).where(
    InviteCode.id == code_id,
    InviteCode.revoked_at.is_(None),
    or_(InviteCode.max_uses.is_(None), InviteCode.used_count < InviteCode.max_uses),
    or_(InviteCode.expires_at.is_(None), InviteCode.expires_at > now_utc()),
).values(used_count=InviteCode.used_count + 1).returning(InviteCode.id)
```

写成「先 SELECT 判断 `used_count`，再 UPDATE」时，两个人同时用同一枚「一人一码」
会双双通过判断、各建一个账号 —— 和刷新令牌轮换是同一类坑（见下面的并发夹具一节）。

### 4. 按人配额（`app/services/quota.py`）

`garment_quota / outfit_quota / tag_quota`，`None` = 不限。三条规则：

1. **只管新增**。上限调小不会让已存在的衣物 / 搭配 / 标签消失 —— 那是用户的数据，
   不该因为管理员改了个数字就被删掉。超了就先拦住新的。
2. **批量按整批算**。一次传 30 张而只剩 5 个名额，整批拒绝并说清楚，
   不要「先存 5 件再报错」—— 那种半成功状态既难解释（哪些进了？）又会留下已落盘的文件。
3. **管理员豁免**（见上一节）。

管理页的用量列**复用同一个计数器**（`count_by_owner`）—— 管理页显示的数字和用户被拦时
的数字对不上，是最容易起争执的地方。

### 5. ⚠️ 预置标签把配额撑爆（发布冒烟撞出来的）

`/auth/quota` 报 `tags: {"used": 131, "limit": 3}` —— 建号时播种 ~130 个标签取值，
全被算进了「可添加标签数量」，任何小于 130 的配额一上来就爆，配额这功能等于没做。

修法：`tag_values.is_seed`（迁移 `0007_tag_seed_flag`，按默认取值目录回填 286 行），
`quota._extra_where("tag")` 只数 `is_seed=False`，`seed_default_categories` 播种时置位。
修完实测 `tags: {"used": 0, "limit": 3}`。

### 6. ⚠️ 访问令牌必须绑会话（发布冒烟撞出来的）

重置密码 / 吊销设备 / 停用账号之后，那个人手上那个访问令牌**还能继续用**（最长 30 分钟）——
JWT 是自证的，服务端不查库根本不知道「这次登录已经被吊销了」。

修法：`create_access_token(user_id, session_id)` 把 `sid`（`user_sessions.id`）写进 payload，
`get_current_user` 每次核对那一行的 `revoked_at` / `expires_at` / `user_id`。代价是一次主键查询。
`decode_access_token` 改成返回 `(user_id, session_id | None)`，**没有 `sid` 的旧令牌当无效**。

### 7. 按用户的大模型

```
users.llm_base_url / llm_api_key / llm_model / llm_from_admin
```

- **不默认注入**：服务器不预置任何模型地址与 Key（`config.vlm_*` 默认空）
- **不同用户互不通用**：`tagger_for_user(user)` 每次**现造** provider。
  `VlmTagger` 只是一组 httpx 参数，没有缓存价值，反而要小心别把 A 的 Key 缓存给 B
  （此前 VLM 是全局单例，第一个用户的 Key 会被所有人生效）
- **用户没填时管理员可代设**：写在同一组字段上，`llm_from_admin` 记来源；
  用户自己保存一次就归自己
- 接口**只回脱敏串**：`mask_key()` → `sk-abc…wxyz`，≤12 位整体打码（别露出前 6 位就是半个密钥）
- `api_key` 三态：不传 = 保持不变、空串 = 清空、有值 = 覆盖。
  用户只改模型名时不必把 Key 重新粘一遍
- 唯一不带密钥的例外是本地 CLIP（`ai_tagger_provider=clip`）：没有地址与 Key 可填，
  属「机器上装没装」而不是「谁的配置」，仍由运维全局开关控制

> **循环导入坑**：`services/llm.py` 顶层**不能** import `app.worker.providers` ——
> `app.worker.__init__` 会 import `pipeline`，而 `pipeline` 要用 `services.llm.tagger_for_user`，
> 于是 `ImportError: cannot import name 'tagger_for_user' from partially initialized module`。
> 办法：所有 provider 在函数内惰性 import（它们只是几个类，开销可忽略）。

### 8. 测试夹具：为什么从内存库换成临时文件库

内存 SQLite 必须配 `StaticPool`，也就是**所有会话共用同一条连接**。于是并发用例的
两个请求落在同一个事务里：落败方 `rollback()` 会把胜方**还没提交**的 INSERT 一起抹掉，
胜方随后报 `FOREIGN KEY constraint failed`。

「同一枚邀请码不能同时注册两个人」这类用例因此失真。夹具改成每个用例一个临时文件库
（`NullPool`，每会话一条独立连接），并发语义才和 PostgreSQL 一致。
另加 `PRAGMA journal_mode=MEMORY` + `synchronous=OFF` 把速度拉回来：全量
**3m23s**（不加速是 11m34s，纯内存库基线约 2m）。锁协议不变，所以并发用例照样有效。

**临时库的收尾（踩过两次坑，别再走一遍）**：

1. 每个用例在 teardown 里删掉自己的 `test.db` / `-wal` / `-shm`，让 pytest 收尾时
   临时目录尽量空 —— 否则几百个 `.db` 会留在那里，收尾的 `rm_rf` 会撞上宿主环境的
   **批量删除保护**（>50 个文件）而抛 `SystemExit`，表现是「进度跑到 100%，但没有
   `passed` 总结行」。
2. **不要**为了这个去加 `--basetemp`。给定 basetemp 时 pytest 的 `tmp_path` 目录名
   不带数字后缀，**函数名前 30 字符相同的用例会复用同一个目录**；上一个用例的库文件
   还在，`create_all` 之后播种就撞 UNIQUE —— 实测一次改动炸出 407 个用例报错
   （既报 `IntegrityError`，也报 `SystemExit`）。
3. 上面两条都做到，收尾仍可能因为残留（句柄未及时释放）超过阈值被拦。**结论不要只看
   终端**，用 `pytest --junit-xml=.verify/junit.xml` 取：报告在收尾清理**之前**写好，
   里面的 `tests / failures / errors` 计数不受影响。

### 三条不能破的规矩

1. **任何会长大的东西都放 `/data`**，绝不写 `/`。两个应用单元都带
   `RequiresMountsFor=/data` —— `/data` 没挂上时它们**故意起不来**：
   SQLite 是「文件不存在就新建」，服务若照常启动，会在系统盘上悄悄造一个空库。
2. **模型目录必须显式给 `U2NET_HOME`**。rembg 默认写 `~/.u2net`，而服务用户的
   家目录在 `/`（SSD）上。
3. **备份这个 SQLite 库不要用 `cp`**（rollback journal 模式下会拷到半截事务），
   用 `/usr/local/sbin/wardrobe-backup.sh`。
